## Как оно в коде?

Представим,что мы разрбатываем соц.сетку и нам можно ставить и получать какое-то количество лайков на постах (спойлер: r/w это read/write).
У нас есть переменная  likes, которая глобальная и 2 функции для нее:getLikes() и setLikes(). Первая увеличиввает переменную likes, а вторая возвращает. Вызываем мы их в main() через горутины по несколько раз, ну и измеряем время
```go
package main

import (
	"fmt"
	"sync"
	"time"
)

var likes int = 0

func setLike(wg *sync.WaitGroup) {
	defer wg.Done()
	likes++
}

func getLike(wg *sync.WaitGroup) {
	defer wg.Done()
	_ = likes
}

func main() {
	wg := &sync.WaitGroup{}
	initTime := time.Now()
	for i := 1; i <= 10; i++ {
		wg.Add(1)
		go setLike(wg)
	}
	for i := 1; i <= 10; i++ {
		wg.Add(1)
		go getLike(wg)
	}
	wg.Wait()
	fmt.Println("Время выполнения проги:", time.Since(initTime))
}

// Вывод: 117.932µs
```

Теперь пусть операции чтения и записи выполняются по 100.000 раз:

Этот вывод говорит нам о том,что гонка данных есть и говорит даже в какой строчке это происходит все 

Но запускать с флашком race на проде нельзя,так как он очень замедляет прогу 

Чтобы избежать гонки можно воспользоваться нами известным sync.Mutex:
```go
var mtx sync.Mutex

func setLike(wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 1; i <= 100_000; i++ {
		mtx.Lock()
		likes++
		mtx.Unlock()
}
}

  

func getLike(wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 1; i <= 100_000; i++ {
		mtx.Lock()
		_ = likes
		mtx.Unlock()
	}
}
// Вывод: Время выполнения проги: 1.185884452s
```

Тут видно,что прога стала выполняться сильно дольше, хотя без мьютекса было быстрее, это все потому что мьютекс выстраивает горутины в очередь и из-за этого тратится больще времени(но это из-за флажка race, без него будет быстрее, поэтому в проде не юзаем) 

Но вернемся к тому,а о чем говорили [[#^7ae99b | выше]] , если надо будет прочесть,то через мьютекс это дело будет идти медленно, так как чтобы до не добраться, горутина должна будет пройти очередь, с другой стороны, без мьютекса нельзя, а то прочитается неверное значение 

Но если бы у нас была гарантия того,что во время чтения значение бы не перезаписывалось, тогда бы можно было бы конкурентно безопасно читать

Это делается с помощью RWMutex:
```go
var mtx sync.RWMutex
```

Имеет методы RLock() и RUnlock(),помимо базовых Lock() и Unlock(), что это такое? Это возможность взять отдельно блокировку на чтение и снять блокировку отдельно на чтение:
```go
func getLike(wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 1; i <= 100_000; i++ {
		mtx.RLock()
		_ = likes
		mtx.RUnlock()
	}
}

//Вывод: 163.272477ms
```

Как видно, программа стала сильно быстрее, почему так?
RWMutex не случайно так называется,так как RLock() и RUnlock() - блокировка на чтение, а Lock() и Unlock() - блокировка на запись. Блокировка на запись понятно как работает. А что насчет чтения? Горутина перед тем,как брать блокировку на чтение сначала посмотрит, есть ли какая-то блокировка на запись,если нет активных блокировок на запись, то у нас может значение прочитаться. Еще в отличии от блокировки на запись, несколько горутин у нас могут брать блокировку на чтение и эт в случае,если не взята блокировка на запись. В итоге и избавляемся от состояния гонки, и пропускаем наши горутины работать в одну секцию параллельно

С записью также, ждет пока горутины прекратят читать 

Зачем же нам тогда обычный Mutex? А все просто, в записи он быстрее чем  RWMutex,поэтому если нужно только записывать, то  Mutex, если читать и записывать, то RWMutex
