Возьмем в нашем `payHandler()` черещ обращение к запросу этот самый  `r.Header`. В коде языка Go Header представляет из себя мапу с ключами и значениями:
```go
type Header map[string][]string
```

Если прогнать  `r.Header`  через цикл,то у нас выведется что-то такое при запросе на `payHandler()`:
```bash
k: Accept --v: [*/*]
k: Postman-Token --v: [f351ec10-7b95-4022-8b96-c9021a1b8131]
k: Accept-Encoding --v: [gzip, deflate, br]
k: Connection --v: [keep-alive]
k: Content-Length --v: [4]
k: Content-Type --v: [application/json]
k: User-Agent --v: [PostmanRuntime/7.49.1]
```

В эту мапу по большому счету зашита всякая служебная информация, допустим у нас есть `k: Content-Type --v: [application/json]`, он указывает на тип отправленного запроса, в данном случает json(об этом будет речь позже) 
![[content_type.png]]

В Postman выбирается тут. Короче, передается тип контента,переданный в теле запроса. Еще есть поле `User-Agent --v: [PostmanRuntime/7.49.1]`, это агент, откуда был отправлен запрос. 

И отсюда вытекает то,что в http-хеддерах зашита всякая служебная информация. Еще там могут быть зашиты токены,благодаря которым мы можем понять,кто отправил запрос. Нужно это для когда у нас есть допустим какой-то кошелек пользователя X. А какой-то пользователь Y делает запрос,мол соверши запрос,но у пользователя Y не должно быть доступа к кошельку пользователя X.  И как раз в хеддере передается токен авторизации. И нащ хендлер уже смотрит, принадлежит ли этот токен авторизации пользователю X. Если да,то запрос совершается,если нет,то нет доступа для проведения данной операции. Это все делается для контроля доступа к информации(чтобы левый человек не получил к ней досуп),но об этом потом.

Благодаря чему можно посмотреть что эти хеддеры в себе хранят,ну и добавить свой, для примера добавлю хеддер "MyHeader" с текстом "Hello Shafi"
